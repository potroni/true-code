# Решения по API записи на занятия

## Брони и лист ожидания

- Создание и увеличение брони учитывают места активных броней. Ожидающие заявки не резервируют места, поэтому свободный остаток доступен клиентам, даже когда первая заявка FIFO целиком не помещается.
- Продвижение выполняется в транзакции первой отмены либо фактического уменьшения брони. Для распределения берется весь свободный остаток после операции, чтобы можно было удовлетворить заявку, для которой места освобождались постепенно. Выход из очереди пересчитывает позиции за счет исключения заявки из числа ожидающих и сам по себе продвижение не запускает. Для отмененного клубом занятия очередь сохраняется без продвижения. Фоновой обработки очереди нет.
- Заявки продвигаются целиком по `(createdAt, id)`. Если очередная заявка не помещается, продвижение останавливается, чтобы сохранить FIFO. Если заявка помещается, срок и остаток абонемента проверяются под блокировкой с учетом возврата в той же транзакции. Срок сверяется по UTC-дате запроса включительно. При просроченном абонементе или недостатке посещений заявка переходит в `closed` без брони и списания, после чего рассматривается следующая.
- Позиция и ограничение одной заявки на клиента и занятие учитывают только статус `waiting`. Успешный перевод создает бронь и сохраняет статус `promoted`. Выход из очереди сохраняет `cancelled` и повторно возвращает тот же `200`. Статусы `closed` и `promoted` сохраняются, чтобы отличать окончание ожидания без брони от создания брони. Созданная бронь отменяется через маршрут отмены брони.
- При входе в очередь состояние занятия проверяется перед наличием действующей заявки, а действующая заявка проверяется перед вместимостью и свободным остатком. Так клиент с действующей заявкой получает `already-waiting`, даже если места появились. Заявка сверх полной вместимости отклоняется, поскольку никогда не сможет продвинуться целиком.
- Двухчасовая граница возврата считается по UTC-времени входа запроса в сервис. Начало занятия проверяется после ожидания блокировок и перед фиксацией изменений. Результат отмены хранится для повторного ответа. Миграция проставляет историческим отменам `refundedVisits = 0`, поскольку фактическая сумма неизвестна, и сохраняет балансы.

## Идемпотентность и транзакции

- Область `Idempotency-Key` — пользователь и операция. Создание брони и вход в очередь имеют независимые области. Отсутствующий, пустой или пробельный ключ дает `400` на обоих маршрутах.
- Журнал хранит только успешные ответы. Повтор с теми же `classId` и `seats` возвращает исходный `201` и тело, включая исходную позицию в очереди. У ключа нет отдельного ограничения длины в приложении. Для уникального индекса используется SHA-256, а исходный ключ проверяется перед выдачей сохраненного ответа.
- Запросы с одним ключом сериализуются транзакционной advisory-блокировкой PostgreSQL, в том числе между экземплярами API. После проверки журнала операции записи блокируют строку занятия, затем все затронутые абонементы по возрастанию ID. Это защищает вместимость и остаток посещений, включая одновременные списания на разные занятия. Журнал и бизнес-изменения фиксируются вместе. При конфликте уникального индекса журнала проигравшая операция полностью откатывается и читает результат победителя.
- При создании брони и постановке в очередь `createdAt` усекается до микросекунд. Это сохраняет совпадение исходного ответа со значением PostgreSQL и точность расчета позиции.

## Дополнительные причины отказа

Все перечисленные ответы имеют статус `409`. Поле `reason` передается на верхнем уровне `ProblemDetails`.

| `reason` | Маршрут и условие |
|---|---|
| `idempotency-key-conflict` | `POST /enrollments` или `POST /enrollments/waitlist`. Успешно использованный в той же области ключ передан с другим `classId` или `seats`. |
| `pass-balance-overflow` | `POST /enrollments/{id}/seats` или `POST /enrollments/{id}/cancel`. Полный возврат превысил бы `int.MaxValue`. Операция отклоняется целиком, чтобы сохранить правило одного посещения на место. |
| `seats-exceed-capacity` | `POST /enrollments/waitlist`. Запрошено больше мест, чем вмещает занятие. |
| `already-promoted` | `POST /enrollments/waitlist/{id}/cancel`. По собственной заявке уже создана бронь. |
| `waitlist-closed` | `POST /enrollments/waitlist/{id}/cancel`. Ожидание по собственной заявке завершилось без брони после проверки абонемента. |

## Карточка, расписание и аналитика

- Карточка каждый раз читается одной проекцией из PostgreSQL по ID брони и владельцу. Запрос включает отмененные брони и занятия и берет текущий остаток абонемента. Redis-кеш карточек оставлен за рамками. Чтение из БД дает актуальный результат после фиксации операций API без инвалидации кеша.
- Расписание использует курсор по `(startsAt, classId)`, чтобы разделять занятия с одинаковым временем начала. Токен кодирует UTC ticks и ID в Base64URL. Границы запроса с точностью меньше микросекунды учитываются при выборе знака сравнения, чтобы сохранить полуоткрытый интервал при микросекундной точности PostgreSQL.
- Аналитика суммирует активные места отдельно по каждому занятию и группирует результаты по залу и UTC-дню в PostgreSQL. Вместимость каждого занятия учитывается один раз. Для крайней нижней даты используется конечная граница SQL, чтобы Npgsql не передал ее как `-infinity`. Для крайней верхней даты используется последняя микросекунда суток, поскольку следующая полночь выходит за диапазон `DateTime`.

## Квота и зависимость от Redis

- Восемь маршрутов задания делят одну квоту на ID пользователя из JWT. Вход, проверка живости и Swagger находятся вне квоты. Лимитер работает после аутентификации, перед проверкой роли и валидацией запроса, поэтому допущенный лимитером запрос учитывается и при последующем ответе `400` или `403`.
- Экземпляры API с общей базой Redis и одинаковым `RateLimiting:KeyPrefix` делят окно в 60 секунд. Lua атомарно удаляет устаревшие отметки и проверяет квоту по времени Redis. После 60 допущенных запросов лимитер возвращает `429` с `Retry-After`.
- API может запуститься при недоступном Redis. При ошибке соединения или тайм-ауте лимитер возвращает `503` до вызова контроллера, чтобы сбой Redis не позволил обойти квоту. После восстановления соединения проверка возобновляется. Ответы лимитера содержат JSON `ProblemDetails` независимо от `Accept`.
- Общая квота зависит от сохранности активных ключей Redis. Вытеснение ключей, потеря данных или переключение на асинхронную реплику могут удалить часть отметок текущего окна.
