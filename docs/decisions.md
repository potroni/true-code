# Решения по API записи на занятия

## Этап 2. Схема и транзакции

### Область ключа идемпотентности

Ключ `Idempotency-Key` действует в рамках пользователя и операции. Создание брони (`POST /enrollments`) и вход в очередь (`POST /enrollments/waitlist`) считаются разными операциями. Два пользователя могут независимо использовать одинаковый ключ. В рамках одной операции занятие не входит в область ключа, поэтому повтор с другим `classId` считается конфликтом.

После успешного запроса повтор с тем же ключом, `classId` и `seats` возвращает сохраненный `201` с исходным телом. Например, если при входе в очередь клиент получил `position: 4`, повтор вернет `position: 4`, даже если с тех пор позиция изменилась. Если изменился `classId` или `seats`, API возвращает `409 ProblemDetails` с `reason: "idempotency-key-conflict"` на верхнем уровне. Это защищает от повторного списания и позволяет клиенту отличить повтор запроса от ошибочного использования ключа для нового действия.

Отдельного ограничения длины ключа в приложении нет. Для уникального индекса используется хеш фиксированного размера, а в журнале сохраняется исходный ключ. Перед выдачей сохраненного ответа проверяется совпадение самого ключа, поскольку хеши разных ключей могут совпасть. Журнал хранит успешные ответы. Запись ответа и бизнес-изменения входят в одну транзакцию, чтобы после отката запрос можно было повторить, а после фиксации получить исходный результат. Обработка конкурентного конфликта индекса, в том числе для запросов к разным занятиям, относится к пункту 3 этапа 2.

Журнал хранит хеш SHA-256, параметры `classId` и `seats` и готовое тело ответа. Все записи соответствуют статусу `201`. При совпадении полного хеша и различии исходных ключей операция завершается внутренней ошибкой без выдачи сохраненного ответа.

В транзакции `Read Committed` после валидации входных данных сначала берется транзакционная advisory-блокировка PostgreSQL по пользователю, операции и ключу. Журнал читается отдельным запросом после получения блокировки. При наличии ответа он возвращается до проверки бизнес-условий, а конфликт параметров обрабатывается как `409`. При отсутствии записи выполняется бизнес-операция в порядке «строка занятия, затем абонементы по ID». `IdempotencyEntryRepository.AddSuccess` добавляет запись в текущий контекст, а вызывающий код сохраняет ее вместе с бизнес-изменениями и фиксирует транзакцию.

При реализации операций записи вызывающий код распознает конфликт вставки по `DbUpdateException` с внутренним `PostgresException`, кодом `23505` и именем индекса `ux_idempotency_entries_user_operation_hash`. В этом случае он полностью откатывает бизнес-транзакцию, отбрасывает ее отслеживаемые изменения и читает запись победителя. Те же правила сравнения действуют для запроса к другому занятию. Другие нарушения ограничений идут по своим путям обработки.

### Блокировки занятия и абонементов

Операция записи открывает транзакцию PostgreSQL с уровнем Read Committed. Для идемпотентного запроса сначала выполняются блокировка ключа и проверка журнала. Затем `Class.LockByIdAsync` блокирует строку занятия, включая отмененные занятия. После получения блокировки операция читает актуальные брони и очередь отдельными запросами и определяет, чьи абонементы могут измениться. Все записи, меняющие занятые места или очередь занятия, должны соблюдать этот порядок.

`Pass.LockByUsersAsync` принимает ID этих клиентов одним набором и блокирует найденные абонементы по возрастанию их ID. При продвижении очереди нужно собрать весь набор до захвата первого абонемента, включая абонемент клиента, отменившего бронь. Порядок блокировок по ID не меняет порядок обработки заявок по FIFO. Срок и остаток посещений проверяются по строкам, прочитанным под блокировкой. Поэтому запросы на разные занятия, затрагивающие один абонемент, последовательно проверяют его остаток.

Оба метода используют `FOR NO KEY UPDATE`. Этот режим сериализует операции записи, захватывающие те же строки, и совместим с блокировкой `FOR KEY SHARE`, используемой при проверке внешних ключей. Методы требуют открытую транзакцию и возвращают свежие снимки без отслеживания EF Core. Для изменения абонемента используйте полученный снимок, присоединив его к контексту до изменения баланса. При выборе участников загружайте только идентификаторы, чтобы в контексте не было ранее отслеживаемой копии абонемента. Транзакция принадлежит вызывающей операции и удерживает блокировки до фиксации или отката.

### Возврат посещений по историческим отменам

Для активной брони `refundedVisits` имеет значение `null`. Для отмененной брони хранится сумма возврата, включая `0`, чтобы повторная отмена могла вернуть тот же результат без повторного пополнения абонемента.

Миграция заполнит `refundedVisits = 0` для всех исторических отмен без сохраненной суммы и сохранит текущие балансы абонементов. Для отмененных броней из сидов ноль отражает отсутствие исходного списания. Для остальных исторических отмен ноль является согласованным значением для неизвестной суммы. Например, повторная отмена такой брони вернет `200` с `refundedVisits: 0` без изменения баланса.

### Состояния листа ожидания

| Состояние | Значение |
|---|---|
| `waiting` | Клиент ждет места. Заявка учитывается при расчете позиции и продвижении по FIFO. |
| `cancelled` | Клиент вышел из очереди. |
| `promoted` | По заявке создана активная бронь. |
| `closed` | При продвижении абонемент оказался просрочен или на нем не хватило посещений. Ожидание завершено без брони. |

Четыре состояния позволяют хранить причину завершения ожидания. При продвижении срок и остаток посещений проверяются по актуальному состоянию абонемента. Если срок истек или посещений не хватает, заявка переходит в `closed` без создания брони и списания посещений. Обработка продолжается со следующей заявкой `waiting`, поэтому первая заявка с неподходящим абонементом не блокирует распределение мест.

### Хранение листа ожидания

В `waitlist_entries` сохраняются клиент, занятие, число мест, время постановки и состояние заявки. Внешние ключи проверяют существование клиента и занятия. Ограничения PostgreSQL допускают только положительное число мест и четыре согласованных состояния.

Частичный уникальный индекс по `(user_id, class_id)` проверяет только строки `waiting`, в том числе при параллельных вставках. После завершения ожидания строка остается в таблице, а клиент может создать новую заявку на то же занятие. Отдельный частичный индекс по `(class_id, created_at, id)` поддерживает чтение очереди занятия по времени постановки. При одинаковом времени первой идет заявка с меньшим ID. Позиция определяется среди текущих заявок `waiting`, поэтому после выхода клиента достаточно поменять состояние его заявки.

Миграция `AddWaitlistEntries` оформлена отдельно, поскольку приложение применяет миграции штатно при запуске и модель EF Core должна соответствовать последней миграции после внедрения таблицы.

## Этап 3. Создание брони

### Доступность мест при обычной брони

`POST /enrollments` определяет доступность по вместимости занятия и сумме мест всех активных броней под блокировкой строки занятия. Ожидающие заявки места не резервируют. Клиент может занять свободные места, даже если первой заявке в очереди требуется больше мест, чем сейчас свободно. Если запрошенное число мест превышает свободный остаток, API возвращает `409` с причиной `capacity-exceeded`.

Это сохраняет единый критерий доступности для обычной брони и позволяет проверять его без чтения очереди. FIFO применяется при продвижении очереди.

### Доступность мест при увеличении брони

`POST /enrollments/{id}/seats` применяет тот же расчет доступности под блокировкой строки занятия. Свободный остаток сравнивается с разницей между запрошенным и текущим числом мест в брони. Если мест на разницу хватает, увеличение разрешено при соблюдении остальных проверок, даже когда первой заявке в очереди требуется больше мест, чем сейчас свободно. Если остаток меньше разницы, API возвращает `409` с причиной `capacity-exceeded`.

Ожидающие заявки не резервируют места. Увеличение сохраняет их позиции, а FIFO определяет порядок продвижения очереди.

## Этап 4. Изменение числа мест

Если возврат посещений при уменьшении брони поднял бы остаток выше `int.MaxValue`, `POST /enrollments/{id}/seats` возвращает `409` с причиной `pass-balance-overflow`. Бронь и абонемент сохраняют исходное состояние, поскольку хранимый остаток имеет тип `int`, а частичный возврат нарушил бы правило одного посещения на место.

## Этап 5. Отмена брони и продвижение очереди

1. При первой отмене распределяем весь свободный остаток после освобождения мест. Это позволяет продвинуть заявку, для которой места освободились за несколько операций.
2. Продвигаем только целые заявки в порядке `(createdAt, id)`. Останавливаемся на первой заявке, которую нельзя удовлетворить целиком, чтобы сохранить порядок FIFO. Свободные места остаются доступны для обычной брони и увеличения брони по правилам этапа 3.
3. Сначала проверяем, помещается ли заявка, затем проверяем срок и остаток абонемента под блокировкой, учитывая возврат в этой транзакции. Срок сверяем с UTC-датой входа запроса на отмену или уменьшение брони в сервис, включая день `validUntil`. Если срок истек или посещений не хватает, переводим заявку в `closed` без брони и списания, чтобы обработать следующую заявку. Заявка, которая не помещается, сохраняет свою позицию.
4. Фактическое уменьшение мест запускает тот же механизм FIFO в одной транзакции с изменением брони. Запрос с прежним числом мест не запускает продвижение.
5. При отмене брони на отмененное клубом занятие возвращаем все посещения независимо от времени. Статусы заявок сохраняем, поскольку создавать брони на такое занятие запрещено, а состояние очереди не должно зависеть от обращения владельца брони.
6. Двухчасовую границу считаем по UTC-времени входа запроса в сервис. Ровно два часа дают полный возврат. При первой отмене проверяем текущее время под блокировкой занятия до чтения очереди, после блокировки абонементов и после записи изменений, перед фиксацией транзакции. Если занятие уже началось и клуб его не отменил, возвращаем `409 class-started` и откатываем транзакцию. Повтор успешной отмены возвращает сохраненный результат.
7. Если полный возврат превысит `int.MaxValue`, возвращаем `409` с причиной `pass-balance-overflow` и откатываем всю операцию. Это сохраняет правило полного возврата и совпадает с поведением при уменьшении брони.

## Этап 6. Вход и выход из очереди

1. Если запрошено больше мест, чем полная вместимость занятия, вход возвращает `409` с причиной `seats-exceed-capacity`. При продвижении целых заявок по FIFO такая заявка никогда не поместится и будет блокировать следующие. Код `409` отражает ограничение конкретного занятия.
2. Выход переводит собственную заявку из `waiting` в `cancelled` и возвращает `200` с ее ID и статусом `cancelled`. Повтор для `cancelled` возвращает тот же результат без записи. Для собственной заявки `promoted` возвращаем `409 already-promoted`, поскольку созданная бронь отменяется отдельным маршрутом со своими правилами возврата. Для `closed` возвращаем `409 waitlist-closed`, поскольку ожидание завершилось при проверке абонемента без создания брони. Исходные статусы сохраняются. Для чужой и отсутствующей заявки возвращаем одинаковый `404`.
3. Отсутствующий, пустой или состоящий только из пробельных символов `Idempotency-Key` дает `400` на HTTP-границе, как при создании брони. Валидный ключ обрабатывается по общим правилам журнала.
4. После HTTP-валидации сначала проверяем журнал. Совпадение параметров возвращает исходный `201`, изменение параметров дает `409 idempotency-key-conflict`. Для нового ключа под блокировкой занятия порядок отказов такой: отсутствие занятия (`404`), `class-cancelled`, `class-started`, `already-waiting`, `seats-exceed-capacity`, `seats-available`. Состояние занятия определяет возможность входа, а `already-waiting` сообщает клиенту о действующей заявке даже при наличии свободных мест.
5. Выход первой заявки сдвигает позиции и сам по себе не запускает продвижение. Продвижение запускают первая отмена брони и фактическое уменьшение числа мест по правилам этапа 5. До следующего запуска свободные места доступны для обычной брони. Выход и продвижение используют общую блокировку занятия. Если первым зафиксирован выход, заявка исключается из FIFO. Если первым зафиксировано продвижение, выход возвращает `409 already-promoted`.

## Этап 7. Расписание

Токен продолжения содержит 16 байт в каноническом Base64URL без заполнения: UTC ticks `startsAt` и `classId` как два 64-битных целых в порядке от старшего байта к младшему. Формат сохраняет всю точность времени и ID и подходит для передачи в строке запроса. При чтении проверяются длина, каноничность кодирования, диапазон ticks и положительный ID. Пустое значение переданного токена дает `400`.
